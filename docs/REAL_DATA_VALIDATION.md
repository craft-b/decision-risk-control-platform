# Real-Data Validation Path

**Status:** all metrics currently published by this project are **pipeline verification on
synthetic data**. This note records why that framing is mandatory and what has to happen before any
number can be quoted as predictive performance. Companion to [AUDIT_FINDINGS.md](AUDIT_FINDINGS.md)
(ML-2) and [DESIGN_SPEC.md](DESIGN_SPEC.md) §3.2.

## Why current metrics are not field performance

All operational data is generated by a fleet simulator. Its failure events were produced by
deterministic age/wear hazard rules evaluated over (a subset of) the same features the model
consumes. A model trained on this data is being graded on how well it re-learns the simulator's own
thresholds — high AUC demonstrates that the snapshot → label → train → serve plumbing is correct,
and nothing more. This circularity is a *known, accepted property of the demo environment*, not a
bug to be papered over with a number.

What the synthetic metrics do legitimately establish, post-remediation:

- Features are point-in-time correct (every window query bounded by `snapshot_ts` — ML-1).
- Labels derive only from actual breakdowns (`eventSource = 'REACTIVE_REPAIR'`), never from
  scheduled PM or model-driven interventions (ML-2/ML-11).
- Rows whose outcome window was cut short by a predictive intervention are censored
  (`label_status = 'censored_intervention'`), not counted as negatives — the standard
  treatment-leakage guard for deployed predictive-maintenance programs.
- The published split has a per-horizon embargo and a by-asset grouped evaluation (ML-3).
- One shared feature transform runs at train and serve time, so there is no train/serve skew
  (ML-6); every preprocessing artifact is resolved by the model's own version (ML-7).
- Probabilities are calibrated at the true prevalence (no SMOTE before calibration), with Brier
  score and expected calibration error published per horizon (ML-5).

## The validation program (Phase B)

1. **Design-partner fleet(s).** One or more rental fleets contribute maintenance history +
   telemetry (or rental-hours proxies for un-telematized units). Asset identity resolution maps
   OEM feeds to internal IDs.
2. **Labels arrive from operations, not rules.** A positive label is a technician-recorded
   `REACTIVE_REPAIR` event (unit failed in service) — the taxonomy and capture UI already exist.
   Labels mature 10/30/60 days after each snapshot by construction; model-performance drift
   tracking starts only once enough labels have realized.
3. **Baseline comparison.** The model is evaluated against the fleet's incumbent policy
   (calendar-based PM), on: failure-class recall at the operating threshold, precision@budget
   (top-K weekly queue, K = shop capacity), and lead time (first HIGH flag → failure; must exceed
   PM scheduling latency ≈ 7 days). ROC/PR-AUC are secondary trend metrics.
4. **Intervention accounting.** Once the fleet acts on model output, intervention-censored rows are
   excluded from evaluation prevalence (already implemented); avoided-failure claims come from the
   censored-cohort comparison, not from raw label counts.
5. **Reporting discipline.** Until step 3 produces numbers, every metrics surface (README,
   dashboard, API metadata) carries `data_source: simulated`. The first quotable field metric is
   grouped-by-asset performance on a partner fleet the model never trained on.
